# SNSから独立した撮影証明 — v1

2026-10-25。ローカル実装・検証済み。本番発行サービスと実機の端末認証は未接続。

## 利用手順

1. ログインし、JustTakenのカメラで写真・動画を撮影する。
2. 「投稿せずに撮影証明を保存」を選ぶ。原本を非公開でアップロードし、既存の端末認証・ファイル照合を通してから署名付き証明を発行する。この操作はpostsテーブルに投稿を作らない。
3. マイページの「あなたの撮影証明」から、1・7・30日有効の証明リンクを作成してOS共有シートで渡す。リンクで渡るのは証明だけ。原本は所有者が別途「原本を元の形式で書き出す」から渡す。
4. 受け手はリンクを開くか、`/verify`に証明JSONを読み込み、原本を選ぶ。ログイン不要。署名・発行元・鍵の失効を確認し、Web Workerで1 MiBずつSHA-256を計算する。ファイルは受け手の端末から出ない。
5. 共有停止は、その証明の既存リンクをすべて失効させる。新規リンクは後から作成可能。保存済み証明・原本のコピーを遠隔削除する機能ではない。

投稿フローでも証明を保存する。SNS投稿だけを削除した場合、保存済み証明と原本は残る。端末の下書きだけを削除してもサーバーで照合済みの原本は残る。原本を消す場合は証明一覧の削除操作を使い、関連投稿も削除して共有を停止する。削除済みの証明情報は無効な記録として一覧に残る。以前の証明未保存の投稿は従来どおり投稿削除時に原本も削除する。

写真はJPEG/HEIF/DNGとHDRゲインマップを含む全バイトを保持。動画は最大60秒、既存の映像・音声を再エンコードしない保存方式を維持する。写真・動画の表示可否に依存せず照合できる。共有先アプリが圧縮・変換したファイルは原本と一致しないので「ファイルとして送信」を案内する。capture-v1の証明対象は旧仕様の縮小済み保存ファイルであり、原画とは表示しない。

## 証明の内容と意味

`justtaken-proof-v1` JSONにES256 Compact JWSを格納し、`typ=justtaken-proof+jws`で既存receiptと区別する。証明本文は厳密なスキーマ。

- 公開用ランダムproofId、アカウントごとのランダムcreatorId。creatorIdはログインした撮影アカウントとの対応を示す仮名IDであり、実名・撮影者本人・著作権を証明しない。同じIDを共有すると複数証明が関連付けられることをUIで伝える。
- 原本全体のSHA-256、バイト数、MIME、寸法、向き、HDR/RAW/動画・音声情報、撮影ポリシー、完全manifestのdigest。
- 端末申告撮影日時、サーバー受付日時、サーバー照合日時、証明発行日時。端末時計は信頼する時刻証明ではない。サーバー時刻も独立した時刻認証ではない。
- Apple App Attest / Google Play Integrityという確認経路、端末環境とサービス環境。どちらかがdevelopment/testなら、本番証明として表示しない。
- scopeは`app-capture-and-file-integrity`。`subjectTruthGuaranteed=false`、`personIdentityVerified=false`を署名に含める。

公開証明にはinstallationId・accountBindingId・nonce・ログイン用userId・メール・位置・元receiptを含めない。証明は現在独自JWS形式であり、C2PA準拠・Content Credentials認定とは称さない。原本へ証明を埋め込む書換えはしない。

## 攻撃への対処と限界

| 対象                                         | 現在の対処                                                                                                                                                               | 残る限界                                                                                                             |
| -------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | -------------------------------------------------------------------------------------------------------------------- |
| 別ファイルへの差替え・再圧縮・メタデータ変更 | ファイル全体のSHA-256とサイズを照合                                                                                                                                      | 自動復元・加工後の同一性推定はしない                                                                                 |
| 証明中のアカウント・日時・hashの変更         | ES256署名、型・発行元・kidを検証                                                                                                                                         | 発行者の秘密鍵が侵害された場合は別途失効・調査が必要                                                                 |
| 外部ファイルの持込・署名要求                 | native所有UUID・撮影前nonce・manifest束縛・App Attest/Integrity・サーバーcounter                                                                                         | 一般の端末認証はカメラセンサー自体のハードウェア署名ではない。OS/アプリ侵害・供給網を完全には排除できない            |
| 盗用証明に自分の名前を付ける                 | 署名内creatorIdは変更できない。SNSキャプションは証明対象外                                                                                                               | 所有者が別途本人確認したIDとの照合がなければ、実名の人物とは結び付かない                                             |
| 共有リンク推測・ログ流出                     | ランダム256-bit secret、サーバーはhashのみ保存。URL fragmentから取得し履歴表示から除去、ヘッダーで送信、no-referrer/no-store、期限・失効・アカウント状態・DO状態を再検査 | リンクを受け取った人は転送可能。ブラウザー拡張・送信先アプリ・アクセスログ設定も信頼境界                             |
| アカウント横断アクセス                       | 所有者認証、capabilityと原本ACLの分離、一覧20件ページング                                                                                                                | 元ファイルを共有した先の複製は制御できない                                                                           |
| 公開鍵差替え・鍵ローテーション               | 同一の信頼済みoriginのJWKS、任意jku/JWKを拒否、kid履歴・失効リスト                                                                                                       | フィッシングサイト自身の署名を信じないよう公式ドメイン確認が必要。TLS/DNS/発行元も信頼する                           |
| 大きなRAW/動画によるメモリ逼迫               | 512 MiB上限、ブラウザーはWorkerで1 MiB逐次hash、nativeのファイル転送                                                                                                     | 空きストレージ、低性能端末の処理時間、OSによる中断は残る                                                             |
| 写真の中身が現実か                           | 撮影経路の証拠を提示し保証範囲を明示                                                                                                                                     | 画面・印刷物の再撮影、演出、AI画像を映して撮る行為は現段階では識別できない                                           |
| 運営による履歴捏造・時刻の改変               | RFC 3161とRekor収録証明を検証し、受け手の履歴と比較する                                                                                                                  | 第三者時刻・公開ログ・受け手の指紋保存を実装。初回受信者への新規証明発行や、運営による検証コード改変は別途対策が必要 |

「改ざん不可能」「AIではないことを完全証明」「本人が撮影したことを実名で認定」と表示しない。署名検証・ファイル一致・リンクの現在状態を分けて表示する。画面上の検証結果スクリーンショットは証明の代替にしない。

## APIと保存

`0004_standalone_proofs.sql`によりprofiles.proof_creator_id、capture_proofs、proof_sharesを追加。原本は既存R2・撮影DOを利用し、二重保存・再エンコードしない。保存枠は投稿と共通の既存quota。

| API                                | 認証          | 意味                                                         |
| ---------------------------------- | ------------- | ------------------------------------------------------------ |
| POST /v1/proofs                    | 所有者Bearer  | VERIFIEDのcaptureから証明を発行。同じcaptureは同じ証明を返す |
| GET /v1/proofs?before=sequence     | 所有者Bearer  | 自分の証明一覧、最大20件・nextCursor                         |
| GET /v1/proofs/:id/location        | 所有者Bearer  | 本人用の撮影位置。署名されたmanifest digestとの一致を再確認。公開証明には含めない |
| GET /v1/proofs/:id                 | 所有者Bearer  | 証明とportable bundle                                        |
| DELETE /v1/proofs/:id              | 所有者Bearer  | 原本・関連投稿削除、証明リンク停止。再送可能。削除記録は残る |
| POST /v1/proofs/:id/shares         | 所有者Bearer  | days=1/7/30、既定7日。最大20個の有効リンク                   |
| DELETE /v1/proofs/:id/shares       | 所有者Bearer  | 現在あるリンクをすべて停止                                   |
| GET/HEAD /v1/proofs/:id/original   | 所有者Bearer  | 非公開原本の無変換ストリーム出力。共有リンクでは取得不可     |
| POST /public/proof-shares/:id      | X-Proof-Token | 証明だけ取得。期限・失効・所有者状態・DOのVERIFIEDを再検査   |
| GET /verify                        | 不要          | 検証ページ。外部コード・analyticsなし、CSP・iframe禁止       |
| GET /.well-known/capture-jwks.json | 不要          | 現在＋過去の公開鍵、revokedKids。秘密鍵の属性は出力しない    |

アプリの書き出しはexpo-file-systemによるnativeダウンロードとexpo-sharing。原本全体をJSのメモリに載せない。書き出した一時ファイルはOSのcacheに置き、24時間を過ぎたものを次回書き出し時に回収する。共有先がシート終了後に読み取る場合があるため直後には削除しない。

## オフライン検証と鍵運用

公開鍵は証明ファイルに同封されたものをそのまま信用せず、公式発行元から別途入手・固定する。CLIは既定でネットワーク通信をしない。第三者署名と収録証明も検証する。`--online` と `--state=history.json` で独立ログの最新連続性と受信者履歴を確認できる。詳細は[外部証明](external-anchors.md)。

```sh
node --import tsx scripts/verify-proof.ts \
  certificate.justtaken-proof.json original.heic trusted-jwks.json https://your-official-api.example
```

開発証明は通常拒否する。テストのみ`--allow-development`を指定する。オフライン結果は取得済み鍵時点の署名とバイト一致であり、現在の鍵失効・共有停止・原本保管状況を示さない。

RECEIPT_PRIVATE_JWK / RECEIPT_KEY_IDは発行用。RECEIPT_PUBLIC_JWKSに過去の公開鍵を保持し、新しいkidへ移行する。kidを別の鍵に再利用しない。REVOKED_RECEIPT_KEY_IDSはカンマ区切り。失効鍵はオンライン検証に使わず、署名鍵を即時ローテーションする。履歴を忘れると過去の証明を検証できなくなる。現在は32本までの旧鍵を想定し、長期運用前に署名サービス分離・永続鍵レジストリ・鍵保管と災害復旧を整える。

本番のAPI_ORIGINは固定のHTTPS公式originが必要。元のoriginを署名に入れるので、安易なドメイン変更は過去証明の信頼設定に影響する。公開前にドメインと鍵運用を決める。秘密鍵・capabilityヘッダーをログに記録しない。
