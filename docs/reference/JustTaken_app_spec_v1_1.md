# JustTaken モバイルアプリ開発仕様書

バージョン 1.1　更新日 2026年10月25日

対象：iOS・Androidアプリ、Cloudflare上のAPI・メディア配信・運営機能。

サービス名はJustTaken（ジャストテイクン）とし、この名称で開発を進める。本書はiOS・AndroidアプリとCloudflare上のシステムを実装・見積もりするための仕様である。今回の更新では名称を統一し、費用と負荷の標準ケースを月間UU100万人・平均DAU20万人に整理した。本文の「本サービス」はJustTakenを指す。名称の予備調査とドメイン候補は第17章に記載する。

## 1 プロダクトの目的と設計判断

### 1.1 提供する体験

自分のスマートフォンで、その場で撮影した写真や短い動画を共有するSNSを作る。撮影は専用アプリのカメラに限定し、投稿には撮影記録の検証結果を表示する。写真・動画を眺める楽しさと、誰かが自分で撮った記録を見られる安心感を両立させる。

中心となる利用体験は「開く、撮る、短い言葉を添える、共有する」。撮影認証の操作や鍵管理をユーザーに要求しない。投稿カードの表示は「撮影記録を確認」とし、詳しく知りたい人だけが検証内容を開く。

本仕様が扱うのは、撮影経路の信頼性と確定ファイルの整合性である。写っている出来事の真偽、事故原因、所有権、撮影同意、撮影対象の著作権までを自動的に証明するものではない。画面に表示した生成画像をカメラで撮り直す行為も、専用アプリ撮影だけでは完全には排除できない。保険会社向けの証拠受付は、別の品質・本人確認・保管要件を定める将来機能とする。

### 1.2 ユーザー要件と初期提案

| 区分 | 本仕様の扱い |
| --- | --- |
| 必須 | 最初からiPhone・Androidアプリとして開発する |
| 必須 | 専用アプリで撮った写真・動画だけを投稿対象にする |
| 必須 | 撮影記録とファイルの一致を検証し、内容を表示する |
| 必須 | Cloudflareを基盤とし、100万人規模で費用が増えにくい構成にする |
| 名称 | JustTaken（ジャストテイクン）を開発名称として採用する |
| 試算基準 | 月間UU100万人・平均DAU20万人。日間UU100万人は拡張比較とする |
| 初期提案 | 日本先行、16歳以上、非公開アカウントが初期値 |
| 初期提案 | 動画は最大30秒・720p、写真は長辺2048px、1投稿1ファイル |
| 初期提案 | 無料保存枠は1人200MB。通常の投稿は期限で自動消去しない |
| 初期提案 | 写真と短尺動画はR2とWorkersで配信し、Streamの常用を避ける |

「初期提案」は開発のための暫定値で、事業方針・実機試験に合わせて変更できる。16歳は本サービスの利用方針案であり、国内法で一律に要求される年齢として扱わない。月間UUは、1か月にアプリを利用した重複のないアカウント数（MAU）として扱う。月間UU100万人・平均DAU20万人を標準とし、平均DAU10万・30万人と日間UU100万人を比較する。DAUの比率は利用予測ではなく試算上の仮定である。登録者総数と過去の保存量は別に管理する。ログイン前と共有Webの閲覧は別集計し、実測時に費用モデルへ加える。

### 1.3 成果の測り方

初回撮影から投稿完了までの離脱率、検証成功率、日次利用継続率、1投稿当たり保存量、1,000閲覧当たりインフラ費用を主要指標とする。初期の数値目標を実績として扱わず、招待制テストの結果から決める。撮影失敗や確認中の待ち時間も、写真・動画別、OS別、端末別に集計する。

初回に含めない機能は、DM、ライブ配信、24時間ストーリー、複数素材の編集、音楽の重ね合わせ、外部画像の転載投稿、長尺動画、有料プラン、広告、生成AIによる画像編集、保険請求の自動判定である。Webは共有先での公開投稿閲覧、規約・ヘルプ・退会受付、運営画面を提供し、投稿はアプリだけで行う。

### 2.2 投稿ルール

1投稿は写真1枚または連続動画1本とする。キャプションは500文字、コメントは300文字、自己紹介は160文字を初期上限とする。文字数は表示上の書記素クラスタで数え、サーバーには別途UTF-8バイト上限を設ける。キャプションの変更は履歴を残し「編集済み」を表示する。メディアの差し替えは認めず、撮り直しは新しい投稿として扱う。

ギャラリー選択、ファイル選択、外部アプリからの共有受信、任意URLからの取込を投稿経路に作らない。プロフィール画像も初回はシステム提供の図形・イニシャルだけとし、ログインプロバイダーの画像を自動で読み込まない。後からアプリ内撮影のアイコンを提供する場合は、切り抜き結果と原本の関係を明示する。

通常のカメラ処理である自動露出・ホワイトバランス・ノイズ低減・手ぶれ補正・圧縮は許可する。「端末内部も含めてAIを一切使用していない」「無加工のセンサー原本」という表現は使わない。運営の不適切コンテンツ検知に機械学習を使うことは、投稿素材の生成・改変禁止と区別して規約に説明する。

### 3.2 代表的な動作

初回投稿では、ログインと規約同意を済ませ、カメラを初めて開いた時にカメラ権限を求める。動画で音を録る時だけマイク権限を求め、拒否された場合は無音で撮れる。撮影後にキャプションを入力し、検証が終われば公開する。検証中の投稿は本人だけに見える。

投稿時の公開範囲は「公開」「承認したフォロワー」「自分のみ」。非公開アカウントでは「公開」を選べない。公開アカウントでもフォロワー限定投稿は可能とする。アカウントを非公開に変更すると、過去の公開投稿も現在のアカウント設定との共通条件で制限する。公開へ戻す時は過去の公開設定も再び有効になることを確認画面で知らせる。

非公開ユーザーへのフォローは申請状態から始める。相手の承認前はメディアも撮影記録も閲覧できない。フォロワー削除とブロックは新規の配信許可を直ちに停止する。すでに発行された短期URLには最大120秒の残存期間があり、保存・画面撮影済みの内容までは回収できない。

ミュートは自分のフィードと通知にだけ影響する。ブロックはログイン中の相互の閲覧・反応・フォローを制限し、相手に通知しない。公開投稿はログアウト閲覧が可能なため、ブロックだけで非公開と同等の保護になるとは説明しない。

### 3.3 エラーの表示方針

| 状態 | ユーザーに見せる案内 |
| --- | --- |
| 一時的な確認障害 | 「記録の確認に時間がかかっています。準備ができ次第、再開します」 |
| 撮影セッション期限切れ | 「撮影記録の有効時間を過ぎました。投稿するにはもう一度撮影してください」 |
| 非対応の撮影環境 | 「この環境では撮影記録を確認できません。投稿の閲覧は利用できます」 |
| 容量上限 | 「保存枠がいっぱいです。設定から不要な投稿を削除すると投稿できます」 |
| 内容審査で保留 | 「投稿内容を確認しています。結果はこの画面と通知でお知らせします」 |
| ファイルの不一致 | 「撮影記録とファイルが一致しません。再送しても解決しない場合は撮り直してください」 |

障害や非対応端末を「偽物」「不正ユーザー」と表示しない。通信再試行と撮り直しが必要な状態を分ける。失敗した素材を黙って別ファイルに置き換えない。

### 3.4 アクセシビリティ

文字サイズ変更、VoiceOver・TalkBack、十分なコントラスト、色だけに依存しない状態表示を必須とする。動画は初期ミュートとし、再生・停止を読み上げ可能にする。写真に任意の代替説明を付けられる。動画の自動字幕生成は初回の必須に含めず、提供時は原音・映像を変更しない別データとして保存する。

## 4 アプリとログインの実装方針

### 4.1 技術構成

UIと業務ロジックはReact Native・TypeScript、開発用ビルドはExpo Development Buildを用いる。撮影・ファイル確定・ハッシュ・プラットフォームの検証API・バックグラウンド送信はSwift・Kotlinの専用モジュールに実装する。Expo GoやWebViewカメラだけで撮影認証を完成させる構成にはしない。[S01]

最低対応OSの初期案はiOS 18・Android 12。公開前に対象端末、カメラ・エンコード能力、App Attest・Play Integrityの対応状況を実機で確認する。SDKと依存ライブラリは実装開始時に安定版へ固定し、互換性テストと更新手順を持つ。OS番号だけで撮影可能と決めない。

ディレクトリは apps/mobile、apps/admin、workers/api、workers/media、workers/jobs、packages/contracts、native/capture を論理単位とする。開発・検証・本番でCloudflare資源、署名鍵、アプリ識別子、OAuthクライアントを分ける。クライアントへCloudflare管理トークンやサービス署名秘密鍵を埋め込まない。

### 4.2 ログインとセッション

AppleとGoogleのIDトークンをサーバーで検証し、issuer・audience・有効期限・nonce・署名を確認する。識別はproviderとsubの組を使う。メールアドレス一致だけで既存アカウントと統合しない。戻ってくるメールや顔写真は必要がなければ保存せず、連絡先の取得を必須にしない。[S02][S03]

アプリのアクセストークンは短期、リフレッシュトークンは端末別にローテーションし、Keychain・Keystoreに保存する。サーバーではリフレッシュトークンのハッシュと失効状態を持つ。不正な再利用を検知した端末セッションを停止し、全端末ログアウトを提供する。アクセストークンに入れた古い公開設定だけでメディア閲覧を許可しない。

ログイン手段を追加する時は直近の再認証を要求し、最後のログイン手段を取り外させない。復旧は連携済みの別手段またはプロバイダーの復旧経路を案内する。運営者がメールだけを根拠にアカウントを引き渡す機能は作らない。パスキー連携は将来拡張点としてインターフェースを分ける。

### 4.3 権限と端末データ

位置情報、連絡先、フォトライブラリの読取権限を初期版で要求しない。GPSを取得せず、画像のEXIFと動画コンテナの位置・端末個体情報は公開原本の確定前に除去する。撮影開始・終了の端末時刻は診断情報として扱い、サーバーの受信・確定時刻と分ける。プッシュ通知は利用場面で任意に許可を求める。

アカウントの表示名とハンドル、投稿、通信ログ、端末の検証情報は個人に関連し得る。メールを保存しないことを「個人情報ゼロ」と表現しない。目的・保存期間・アクセスできる運営担当を定める。

## 5 ネイティブ撮影

### 5.1 撮影経路と信頼の範囲

投稿対象は iOS／Android アプリ内で撮った写真・動画だけとする。Swift／AVFoundation、Kotlin／CameraX と必要な MediaCodec を使う。ギャラリー、共有、外部ファイル・外部カメラ・画面収録は取り込まない。Web は閲覧用とする。

ネイティブモジュールはカメラ出力から非公開の `captureHandle` を発行し、保存・最適化・サムネイル生成・ハッシュ・証跡要求を管理する。UI には撮影開始・停止・確定・破棄だけを公開する。任意の bytes・URL・パスを署名する API は設けない。ハンドルをセッションに結び付け、確定後の変更を禁止する。撮影から証跡生成までの重要経路は OTA 更新で差し替えず、署名されたストア配布版で更新する。

これは正規実装の経路制限であり、センサーとファイルの関係の数学的証明ではない。侵害されたプロセスによる差し替えや鍵の不正使用は、ハードウェア保護鍵を使っても残存リスクとなる。

### 5.2 保存する原本と容量上限

「原本」は専用カメラの出力をネイティブで最適化し、メタデータ整理まで終えて最初に確定したアップロード用ファイルとする。保存対象はこの原本とサムネイルであり、RAW・高解像度中間データ・4K 動画は別保存しない。

| 対象 | 初期仕様 | 上限の扱い |
|---|---|---|
| 写真原本 | JPEG、sRGB、長辺 2,048 px 以下、目標約 350 KB | 1 MiB 以下。目標容量は保証値ではない |
| 写真サムネイル | JPEG、長辺 480 px 以下 | 64 KiB 以下 |
| 動画原本 | SDR、H.264／AAC-LC、MP4、720p 以下、30 fps 以下、30 秒以下 | 6 MiB 以下 |
| 動画ビットレート | 映像目標 1.1 Mbps、音声目標 64 kbps | コンテナを含む総量は約 1.2 Mbps を目安とし、実サイズも検査 |
| 動画ポスター | 同じ撮影動画から生成した JPEG、長辺 480 px 以下 | 64 KiB 以下。外部画像を指定不可 |

縦動画の最大外枠は 720 × 1,280、横は 1,280 × 720 とする。ビットレートは目標値なので、時間・解像度・実サイズを個別検査する。超過時はコミット前に同じハンドル内で再圧縮し、適合できなければ確定しない。切り抜き・合成・美肌・生成補完・任意フィルターは提供しない。通常の露出・ピント・手ぶれ補正・端末画像処理・縮小・圧縮は許容する。

### 5.3 確定処理

順序は「撮影・エンコード終了 → 向き・メタデータ整理 → faststart 化 → サイズ検査 → サムネイル生成 → 全 SHA-256 計算 → manifest 確定」とする。JPEG は向きを画素へ反映する。MP4 は必要な向き・色・音声を保持し、`moov` を `mdat` より前に置く。AVAssetWriter／Recorder と必要な再多重化の完了を待って確定する。

メタデータは許可リスト方式で GPS・シリアル・任意 XMP・位置タグ等を除去する。ハッシュ後のメタデータ変更や faststart 化は禁止する。端末原本はアプリ専用領域に保存し、バックアップを除外し、不要な中間ファイルを削除する。送信は iOS の background URLSession、Android の WorkManager と連携する。OS の実行制限や利用者による強制終了後まで必ず継続するとは保証せず、再起動時に期限内の未完了送信を復帰させる。

サムネイルも同じハンドルから生成して manifest に含める。原本との関係はハッシュだけでは証明できず、ネイティブ実装を信頼する。初期版は動画をサーバー再エンコードせず、確定した MP4 を R2 から配信する。

## 6 撮影記録の検証

### 6.1 状態と期限

| 証跡状態 | 内容と次の処理 |
|---|---|
| `ISSUED` | サーバーが撮影用 nonce を発行。5 分以内にコミットする |
| `COMMITTED` | manifest と端末検証が承認され、nonce を一度だけ消費。内容を固定する |
| `UPLOADING` | 確定済みファイルを送信。コミット承認から 24 時間以内 |
| `VERIFYING` | 全ファイルのハッシュ、サイズ、メディア仕様を照合する |
| `VERIFIED` | 撮影記録の検証完了。公開可否の別審査へ進む |
| `EXPIRED`／`REJECTED`／`CANCELLED` | 期限切れ、検証不一致、利用者による取消。元の状態へ戻さない |

通信障害は期限内に再試行する。公開には `VERIFIED`、全メディア準備完了、モデレーション許可、アカウント有効をすべて要求する。証跡の検証完了と公開許可は同義ではない。

### 6.2 API と manifest

| API | 契約 |
|---|---|
| `POST /v1/capture-sessions` | 認証済み利用者に sessionId、32 bytes のランダム nonce、serverIssuedAt、commitExpiresAt、policyVersion、容量上限を返す |
| `POST /v1/capture-sessions/{id}/commit` | manifest、platformProof、冪等キーを受け付ける。承認時に serverCommittedAt と uploadExpiresAt を返す |
| `PUT /v1/assets/{assetId}/content` | コミット済み asset の内容だけを受け付ける。保存先キーと期待ハッシュはサーバーが決定する |
| `POST /v1/capture-sessions/{id}/complete` | 必須 asset が揃ったことをサーバーが検査し、検証処理を進める |
| `GET /v1/capture-sessions/{id}` | 状態と送信済み asset を返す。応答喪失や再起動からの復帰に使う |

manifest は UTF-8 JSON を RFC 8785 の JCS で正規化する。[S06] 数値は整数、日時は UTC 文字列とし、未知フィールド・重複キー・不正値を拒否する。以下のハッシュ等は説明用の値である。

```json
{
  "version": 1,
  "policyVersion": "capture-v1",
  "sessionId": "cs_1",
  "installationId": "in_1",
  "accountBindingId": "ab_1",
  "clientCaptureId": "cc_1",
  "nonce": "<nonce>",
  "clientCapturedAt": "2026-10-25T08:00:03Z",
  "kind": "photo",
  "assets": [
    {
      "id": "original", "role": "original", "mime": "image/jpeg",
      "bytes": 349000, "width": 2048, "height": 1536,
      "sha256": "<64桁のSHA-256>"
    },
    {
      "id": "thumbnail", "role": "thumbnail", "mime": "image/jpeg",
      "bytes": 42100, "width": 480, "height": 360,
      "sha256": "<64桁のSHA-256>"
    }
  ]
}
```

動画は durationMs、映像・音声 codec、fps の整数分子・分母を含め、ポスターも asset とする。asset の順序・役割を固定し、追加・欠落を拒否する。証跡には `manifestDigest = SHA256(UTF8("CAPTURE_SNS_V1") || 0x00 || UTF8(JCS(manifest)))` を渡す。

発行・承認時刻はサーバーが記録する。`clientCapturedAt` は端末の申告値である。発行から承認までの時間幅を、厳密なシャッター時刻や撮影場所の証明と表示しない。

### 6.3 iOS と Android の検証

iOS は初回に App Attest 鍵と登録用チャレンジで attestation を取得する。サーバーは Apple の証明書連鎖・アプリ識別子・環境・チャレンジ等を公式手順で検証し、公開鍵とカウンターを登録する。コミットごとに `manifestDigest` を `clientDataHash` とした assertion の署名・識別子・カウンター増加を検証する。同一インストールのコミットは直列化する。App Attest 鍵は汎用署名鍵として扱わない。[S04]

Android は Play Integrity Standard の `requestHash` に `manifestDigest` の base64url 表現を指定する。サーバーが Google でトークンを検証し、requestHash・発行時刻・パッケージ名・承認済み署名証明書と版・`PLAY_RECOGNIZED`・`MEETS_DEVICE_INTEGRITY` を確認する。初期版は Google Play 配布限定のため `LICENSED` も必須とする。鮮度上限は 120 秒を初期値とし、自動再生防止に加えて独自 nonce を一度だけ消費する。[S05]

Play Integrity と Keystore の署名・ハードウェア鍵認証は別物である。後者を実装していない初期版では「端末内の専用鍵が写真に署名」と説明しない。どちらの OS の検証も、画素が必ずカメラ由来であるとの保証ではない。

### 6.4 原子的コミットと投影

インストール単位の Durable Object を nonce・登録鍵・iOS カウンター・セッション・冪等キー・manifest の正本とする。外部検証後、DO の単一トランザクションで nonce 未消費・期限・アカウント・カウンター増加・冪等キーを再確認し、nonce 消費・カウンター更新・COMMITTED・応答・outbox を原子的に保存する。

同じキー・同じ manifestDigest の再送には保存済み結果を返し、別内容なら 409 とする。Google トークンの再検証前にも結果を調べ、トークンの再生検知で正当な再送を失敗させない。nonce の期限は DO の承認時点で判定する。

D1 内の撮影状態は一覧・検索用の投影とし、outbox をイベント ID で冪等反映・再配送する。この扱いは撮影状態に限り、投稿本文・フォロー等の SNS 業務データは D1 を正本とする。DO・D1・R2 間の一括トランザクションは仮定しない。撮影状態照会とアップロード認可は DO を確認し、投影遅延で未承認メディアを公開しない。

### 6.5 R2 への固定保存

asset PUT は Worker 経由で非公開の `staging` に保存する。認証・コミット・期限・asset・期待サイズを確認し、期待 SHA-256 を R2 の `sha256` に渡す。`onlyIf: new Headers({"If-None-Match": "*"})` で上書きを拒否し、受信実バイト数の超過も中止する。アプリへ汎用資格情報を渡さず、キーを再利用しない。[S07]

`complete` 後、各 staging を 1 回 GET し、その同じストリームをサイズ・ハッシュ・形式パーサで逐次検査しながら `originals` に転送する。originals PUT にも期待 SHA-256 と同じ条件を指定する。形式・解像度・時間・codec・メタデータを最後まで検査し、全 asset の保存と検証票保存が成功するまで `VERIFIED` にせず、originals も配信しない。全メディアをメモリ展開せず、パーサと転送のバッファを制限する。

可変 staging の先行ハッシュ検査後に別 GET でコピーする方法や、HEAD 後の無条件 PUT は禁止する。検査した bytes と保存した bytes を一致させ、ETag を SHA-256 の代用にしない。通常系は本体とサムネイルそれぞれの staging PUT・originals PUT、および検証票 PUT で Class A 5 回、staging GET 2 回で Class B 2 回とする。再試行・復旧の照合、配信 GET 等は別計上する。

条件不一致時は既存チェックサム・サイズ・サーバー設定情報を照合し、同じ成功済み送信だけを成功扱いにする。R2 成功直後の停止もこの照合で復旧する。期限切れ・検証失敗の物を回収し、削除を正本に記録して遅延送信による復活を防ぐ。不変とは保存 API の上書き禁止であり、管理権限まで制限した WORM 保存ではない。

### 6.6 障害・再インストール

| 条件／エラー | 動作 |
|---|---|
| `SESSION_EXPIRED` | 発行から 5 分を超えたコミットを拒否し、再撮影を案内 |
| `UPLOAD_WINDOW_EXPIRED` | 承認から 24 時間を超えた送信を拒否。猶予を再試行で延長しない |
| `PROOF_TEMPORARILY_UNAVAILABLE` | 状態を維持し期限内に再試行。利用者を不正扱いしない |
| `MANIFEST_CONFLICT` | 同じ冪等キーへの別内容を 409 で拒否 |
| `CONTENT_HASH_MISMATCH` | 422。保存・公開せず、確定した同じファイルの再送を案内 |
| `MEDIA_POLICY_VIOLATION` | 422。コミット済み manifest の書き換えは認めず、必要なら再撮影 |
| `UNSUPPORTED_CAPTURE_ENVIRONMENT` | 閲覧のみ。認証を省略して投稿させない |

完全オフラインでは開始できない。取得後の切断は 5 分以内のコミット、承認後の切断は確定ファイルを保持して 24 時間以内の再送で回復する。再起動時は状態照会する。再インストール・鍵喪失は新 installation と鍵登録が必要で、旧セッションを付け替えない。ログアウトでカウンターを戻さない。開発ビルド・シミュレーター・認証非対応端末は本番投稿不可とし、開発環境を分離する。

## 7 証明表示と不正への対応

### 7.1 表示する意味

バッジは **「撮影記録を確認」** とする。詳細は「本サービスの専用カメラの撮影記録を検証し、保存ファイルが確定時の記録と一致することを確認しました。サイズ調整・圧縮を行っています。写っている内容の真実性を保証するものではありません」とする。

「本物 100％」「AI 関与ゼロ」「完全無加工」「本人撮影」「事故の事実を証明」と表示しない。AI 画像の画面・印刷物・演出された事故も撮影できる。本人確認、権利・撮影許可、場面の真偽は撮影証跡と別である。

サービス検証票は ECDSA P-256 の JWS とし、protected header の `alg` を `ES256` に固定して `kid` を含める。payload は `manifestDigest`、全 `assetHashes`、`policyVersion`、`serverVerifiedAt` 等とする。専用 signer Worker が DO の全 asset 検査完了記録を確認して署名し、秘密鍵を Worker secret で管理する。検証票を保存後に `VERIFIED` へ進める。公開側には installationId・nonce・個人識別子・正確な位置を含めない。

検証票の時刻・payload・kid・保存先を署名前に固定し、再試行では保存済みの正当な検証票を再利用する。ES256で再署名して同じbytesになることを前提にしない。保存後・DO更新前に停止した場合は署名とpayloadを照合して復旧し、VERIFIEDへの遷移時に取消・削除・revisionを再確認する。

通常の鍵更新後も旧公開鍵で検証を継続する。鍵侵害時は失効台帳で対象検証票を無効化し、現在の有効性はオンラインで確認する。検証票にも投稿と同じ ACL・非公開化・削除を適用する。C2PA／Content Credentials 互換は後続とし、この独自検証票を C2PA 認証済みとは呼ばない。[S08]

### 7.2 脅威と対応

| 脅威 | 対策と残る範囲 |
|---|---|
| 外部・生成ファイルの取り込み | ネイティブ専用ハンドル、取り込み機能なし、端末検証。侵害された実行環境による偽装は完全排除できない |
| 通信内容・サムネイルの差し替え | 全 asset のハッシュを manifest に結び付け、保存時と配信対象を固定 |
| nonce・トークンの使い回し | 短期 nonce、DO の原子的消費、カウンター、冪等処理 |
| 画面再撮影・虚偽の演出 | 技術保証の対象外。通報、説明ラベル、審査で対応し、AI 推定を証明とは扱わない |
| 再インストールによる乱用 | アカウント単位の制限と監視。installationId を永続的な本人識別子とは扱わない |
| 検証済み投稿の権利侵害 | 独立した通報・削除・異議申立て。バッジを審査免除にしない |

### 7.3 受入基準

実機で指定上限・GPS 等の除去を検査する。原本・サムネイルの 1 byte 変更、asset 欠落、別アカウント流用、期限切れ、nonce 再利用を拒否する。同時コミット・再送・応答喪失で投稿やカウンター消費を二重化しない。

並行 PUT の上書き拒否、処理停止・D1 障害・再起動からの回復を確認する。MP4 は同じハッシュで先頭から再生でき、検証前・削除後は公開されない。画面再撮影が通り得ることも試験し、その限界と矛盾する保証を UI・規約・紹介資料に置かない。

## 8 Cloudflare構成

### 8.1 採用構成

本サービスはiOS／Androidアプリ、Workers Paid、D1、Durable Objects（以下DO）、R2、Queuesで構成する。保存量と処理回数を管理し、Stream、サーバー側ffmpeg、Containersは初期必須構成に含めない。動画は有料Developer Platformの経路で扱い、無料CDNだけで無制限配信できると説明しない。[S12]

| 構成要素 | 責務 |
|---|---|
| モバイルアプリ | 撮影・形式確定・端末検証・投稿・閲覧 |
| API Worker | 認証、入力検証、D1ルーティング、容量予約、投稿・SNS API |
| Media Worker | 120秒の閲覧grant検証、画像配信、MP4のRange配信、キャッシュ |
| Security DO | installation単位の登録鍵（iOS）・端末検証、nonce、ledger、outbox |
| D1 | プロフィール、投稿、フォロー正本、フィード、容量台帳、管理業務 |
| R2 | 非公開のstaging、確定済みoriginals、サムネイル、証跡ファイル |
| Queues | DOからD1への反映、fanout、通知、削除、再処理 |

Security DOはinstallationごとに置く。撮影セッション単位や全利用者共通のDOは作らない。アカウント単位の容量・投稿一覧はD1を正本とし、複数端末で共有する。

### 8.2 撮影から公開までの確定処理

1. `POST /capture-sessions`でSecurity DOがinstallation・ユーザー・期限に束縛したnonceを発行する。ネイティブモジュールが撮影・形式確定・ハッシュ・端末検証を行う。
2. `/capture-sessions/{id}/commit`でmanifest等を検査し、D1容量予約を確保する。DOのtransactionでnonce消費、カウンター更新、manifest、`COMMITTED`、応答、outboxを固定する。これはアップロード前の内容確定であり、実ファイル検証完了ではない。
3. `PUT /assets/{assetId}/content`でWorkerを経由してprivateなstagingへ送る。DO正本のcommit・期限・assetと実バイト数を確認し、汎用R2資格情報は配布しない。
4. `/capture-sessions/{id}/complete`から検証を進める。stagingの単一GETストリームを、サーバー専用originalsの新規キーへchecksum付きPUTする。期待SHA-256、新規作成条件、形式・寸法・長さ・実サイズを検査し、全量をメモリ展開しない。[S07]
5. 全assetの固定・実体検証後、レシートを保存し、DOが`VERIFIED`とoutboxを原子的に記録する。事前の`COMMITTED`と区別し、D1行だけで認証済み表示を作らない。
6. Queues経由でcapture projection、容量予約消費、処理済みイベントを同じuser home D1のtransactionへ反映する。投稿intentは非公開の`PROCESSING`で保存し、検証・審査完了後にサーバーが自動公開する。アプリ終了後も処理を継続する。

DO・D1・R2間に原子的transactionはない。DO更新後のD1失敗は同じイベントの再送で復旧する。R2固定後のDO失敗は照合・回収する。stagingを認証原本や配信先にしない。原本＋thumbの2 PUT、固定用2 GET＋2 PUT、レシート1 PUTを通常経路とし、再試行等は追加操作として計測する。

### 8.3 冪等性と認証表示

更新APIは`Idempotency-Key`を要求し、同一キー・異なるpayloadには409を返す。Queueの重複・順序逆転は`event_id`一意制約と`revision`で処理する。nonce再使用、captureの不正な付替えを拒否する。

認証表示は撮影経路と提出後の整合性を示し、被写体の真実性・説明の正しさ・再撮影防止を保証しない。

## 9 データ配置と主要テーブル

### 9.1 論理bucketと物理D1

初期構成はSNS用D1を4個、directory用D1を1個とする。`stable_hash(user_id) mod 256`で論理bucketを決め、4個の物理D1へ配置する。256個のDBを作る意味ではない。directoryにはハンドル一意性、ユーザーID、ルーティング管理を置く。

repositoryは`bucket_id`とrouting versionを受け取り、業務コードへ物理DB名を埋め込まない。物理DB数を増やしても論理bucketは変えない。1 DB当たり10 GB上限、問い合わせ遅延、集中負荷を監視してbucketを移動する。[S10]

### 9.2 D1の主要テーブル

各テーブルは必要な`bucket_id`、時刻、revisionを持つ。メディアと長い証跡JSONはR2に置く。

| テーブル | 正本・配置と主要項目 |
|---|---|
| `user_directory` | directory。`user_id`、一意なhandle、home bucket、アカウント状態 |
| `login_identities` / `auth_sessions` | provider＋subjectの一意対応。user homeのrefresh token hash、期限、失効・rotation状態 |
| `bucket_routes` | 管理用。bucket、物理DB、routing epoch、移動状態 |
| `profiles` | user home。表示名、公開設定、状態、ACL revision |
| `posts` | author home。ID、capture、種別、本文、状態、公開時刻 |
| `media_assets` | author home。role、R2キー、SHA-256、サイズ、寸法、長さ、形式 |
| `capture_projection` | DO反映。installation、capture、revision、receipt、検証時刻 |
| `followers` | target author homeの正本。target、follower、申請／承認状態、revision |
| `following_projection` | follower home。一覧用。認可には使わない |
| `blocks` | blocker home。blocker、対象、revision。相手側へ別途反映 |
| `feed_inbox` | recipient home。recipient、post ID、author、公開時刻、失効時刻 |
| `reactions` / `comments` | 対象投稿側。利用者、post ID、本文等、状態。reactionは組合せを一意化 |
| `bookmarks` / `mutes` | user home。保存post・mute対象。組合せを一意化 |
| `notifications` / `push_devices` | user home。通知event・既読、OS・push token・有効状態 |
| `caption_revisions` | author home。post、旧新版、編集者・時刻。媒体の証跡と分離 |
| `quota_accounts` | user home。上限、使用済みbytes、予約済みbytes、revision |
| `quota_reservations` | user home。予約ID、capture、bytes、状態、期限、event ID |
| `outbox` / `processed_events` | 状態変更と同時に記録。送信・重複排除 |
| `reports` / `admin_actions` | 通報、対象参照、対応状態、担当・理由、操作監査 |
| `export_jobs` / `deletion_jobs` | 要求、進捗、期限、結果、対象、再試行 |

投稿状態は`DRAFT / PROCESSING / READY / PUBLISHED / HIDDEN / DELETED`とする。未投稿保存はDRAFT、投稿intent受付後はPROCESSING、検証・審査完了はREADY、公開はPUBLISHEDとする。`capture_id`に投稿一意制約を置き、同じcaptureから複数投稿を作らない。削除・非表示後の遅延イベントで再公開しない。

投稿一覧は`(bucket_id, author_id, published_at, post_id)`、inboxは`(bucket_id, recipient_id, published_at, post_id)`を索引化し、時刻＋IDのcursorでページングする。集計値は再構築可能にし、全再生を共通行へ書かない。

### 9.3 Security DOの保存範囲

Security DOにはiOS登録鍵・失効状態、端末検証結果、nonce消費状態、ledger、outboxを置く。ledgerはユーザー・capture ID、manifest digest、assetのハッシュ・参照、確定時刻、receipt鍵ID、revisionを記録する。

Queue送信成功とD1反映完了を区別し、同じevent IDで再送できる。定期照合で未反映ledger、未完了予約、孤立R2オブジェクトを検出する。

### 9.4 フォローと非公開権限

follow／承認／解除はtarget author側の正本とoutboxを同じtransactionで更新する。follower側一覧とinboxは非同期projectionとし、cross-DB JOINを前提にしない。

非公開grant発行時はauthor側primaryの公開設定・投稿状態・承認followを読む。遅れたprojectionで認可しない。ブロックも当事者側正本を確認し、不明なら発行を保留する。同じauthor／shardへの照会をまとめ、RangeごとのD1照会を避ける。

## 11 配信と費用制御

### 11.1 保存形式を撮影時に固定する

| 種別 | 初期仕様 |
|---|---|
| 写真原本 | JPEG、長辺最大2,048 px、最大1 MiB |
| 共通thumb | JPEG、長辺最大480 px、最大64 KiB |
| 動画原本 | MP4、H.264、SDR 8 bit、720p、最大30 fps、最大30秒 |
| 動画圧縮 | 映像目標1.1 Mbps＋AAC-LC音声64 kbps。合計約1.2 Mbpsを目安 |
| 動画サイズ | 最大6 MiB。目標bitrateとは独立したhard limit |

原本はネイティブ撮影モジュールが上記仕様で確定したファイルとする。RAW・別の高解像度原本・表示用コピーは保存しない。原本＋thumbを基本単位とし、thumbも同じ撮影から生成する。

リサイズ・圧縮・mux・faststart・不要metadata除去はハッシュ・manifest確定前に完了する。manifestに全assetのrole、ハッシュ、サイズ、寸法、生成versionを含める。commit後は媒体を変換せず、caption等を別データで管理する。

Androidのstreamable出力指定は保証ではないため、最終MP4の`moov`位置を検査し、再muxはハッシュ前に行う。[S11] 動き・暗所・端末差の品質試験に通らなければ解像度・bitrate・尺を改訂する。

### 11.2 grant、Range、キャッシュ

grantのTTLは120秒とする。Workerはasset・variant・期限・閲覧sessionへの束縛を検証してからcacheを参照する。ログイン閲覧ではgrantのviewerIdとsessionIdを、署名付きのメディアsession cookieの値と照合する。URLだけを別ユーザーへ渡しても非公開素材を取得できないようにする。公開投稿の匿名閲覧は匿名sessionを発行し、grantと結び付ける。共有cache keyはasset ID＋variant＋不変revisionとし、tokenと個人IDを含めない。外部応答はprivateとし、R2公開URL等の迂回経路を作らない。

メディアsession cookieはSecure、WebではHttpOnly・適切なSameSiteとhost制限を用い、ネイティブではセッションを安全に保存してプレイヤーの要求へ渡す。iOSではAVURLAssetHTTPCookiesKey等の公開APIを使う。Media Workerはcookieとgrantの署名・期限をローカルで検証し、RangeごとにD1へ照会しない。grantの期限がsessionの期限を超えないようにする。ログアウトで端末のcookieを消し、新しいgrant発行を停止する。すでに発行した両tokenのコピーには最大120秒の残存がある。[S28]

非公開化・解除・ブロック・削除後は新しいgrantを発行しない。既発行分は最長120秒有効で、取得済みbytesや進行中の転送は回収できない。revisionの記載だけで即時失効できるとは扱わない。

MP4は`HEAD`、単一`Range`、`206`、`Content-Range`、`Content-Length`、範囲外の`416`、強いETagに対応し、byte範囲を変える圧縮変換をしない。Cache APIは206を保存できないため完全な200のみ保存する。cache missはR2のRange読出し、完全200があればcacheのRange切出しを使う。[S09] 人気動画の先読み充填は追加最適化とし、高いhit率を費用の保証値にしない。

動画は画面内の1本だけ再生し、全件先読み・画面外再生を止める。R2のegress無料でも保存量と各サービスの操作料金は残る。閲覧数とHTTP回数を区別し、Range・seek・再試行・thumb取得を測る。

### 11.3 容量予約と無料枠

無料保存上限の初期提案は200 MB（200,000,000 bytes）。原本・thumb・レシート・確定済み下書きを実サイズで数える。レシートは生成上限分も事前予約して精算する。stagingは別の短期容量予約と同時upload数制限で多重溜め込みを防ぎ、永続枠との二重計上を避ける。

user home D1で`使用済み＋予約済み＋今回予約≦上限`の場合だけ予約する。予約の`COMMITTING`はcapture状態とは別とし、DOのVERIFIED反映で実サイズを使用済みへ移す。staging削除後に短期予約を解放する。

期限だけで処理中予約を解放しない。DO確定済み・D1未反映を考慮し、ledger・outbox・R2を照合する。削除容量は物理削除後に一度だけ返す。上限到達時も閲覧を維持し、新規投稿に容量整理を案内する。

## 12 運用と拡張

### 12.1 フィードと負荷制御

小規模authorは直近activeなfollowerへpost IDをfanoutし、最大1,000 recipient／投稿とする。超過authorはpullし、閲覧時に最近の投稿をmergeする。inactiveへのfanoutを止め、復帰時に再構築する。

inboxは最新500件または7日間の短い方まで保持し、過去分はプロフィール等から取得する。post ID・author・時刻等だけを保存し、inbox残留を理由に閲覧grantを発行しない。

API・投稿・再送に回数上限を設ける。費用アラートは請求上限ではなく、異常時に投稿・先読み・再試行を抑制する。

### 12.2 bucket移動とデータ回復

SNS用D1は約6 GBまたは継続的な遅延悪化を分割検討の目安とする。6 GBは運用上の余裕である。4→8→16 DBへの拡張はbucketコピー、outbox差分追随、短い書込停止、routing epoch切替の順で行う。

旧DB側のwrite fenceで古いWorker・route cacheの書込を拒否する。件数・参照・未処理イベントを照合し、復旧手順を残す。routing変更だけで移行完了としない。

### 12.3 削除、export、監視

削除要求で新規grant・掲載・コメント追加を止め、非同期に原本・thumb・証跡・projectionを削除し、cache purgeと容量返却を行う。原本に永久lockを設定せず、通報等の保全は目的・権限・期限を分ける。

exportは本人認証後、本人のデータ・原本・証跡をまとめて期限付きで提供する。他者の非公開情報や管理記録を除く。退会はアプリから開始しjobで追跡する。バックアップを含む削除期限はデータ保持方針に従う。

検証失敗率、DO→D1遅延、未完了予約、孤立R2、Queue滞留・DLQ、DB容量・遅延、再生開始時間、利用量を監視する。token・署名URL・不要な位置情報をログに残さず、管理操作は担当者・理由・時刻を記録する。

### 12.4 受入基準と拡張ゲート

- 再送で投稿・容量消費・通知が重複しない。
- DO確定後の障害から、撮り直しなしでD1と容量台帳を復旧できる。
- 複数端末の同時投稿で容量超過・予約の二重解放が起きない。
- staging差替えで確定原本のハッシュ・配信内容が変わらない。
- サイズ超過・形式不適合・署名不整合を公開前に拒否する。
- 両OS実機で再生・seek・Range・再試行・通信復帰が通る。
- 削除等で新規grantを止め、既発行分の猶予は120秒以内となる。
- bucket移動中も欠落・二重更新・旧DBへの書込を防ぐ。
- 月間UU100万人・平均DAU20万人を標準とし、10万・30万DAUの感度と100万DAUへの拡張を分け、ピーク・人気投稿集中・fanout・cache missの負荷試験を拡張ゲートとする。

## 13 安全対策とプライバシー

### 13.1 投稿の審査

撮影記録が確認できても、投稿内容が適切とは限らない。撮影記録の状態と内容審査の状態は独立して管理する。通報・ブロック・運営への連絡先・利用規約への同意を初回リリースに含める。AppleとGoogleのUGC要件を公開直前にも確認する。[S13][S14]

全員の投稿を人が見る前提で100万人規模の費用を見積もらない。招待制テストでは人手審査を併用し、公開運用では自動フィルター、リスク別の保留、通報、人手判断を組み合わせる。自動検知は生成物か否かの証明に使わず、規約違反の可能性を絞る用途に限定する。動画はポスター1枚だけで安全と判断せず、動画の内容と音声を評価できる審査方式を採用する。

モデレーションの実装は vendor adapter と判定ルールを分け、費用、検出漏れ、誤検知、日本語の扱い、非公開投稿の委託条件を評価する。採用サービスと担当者が決まるまで一般公開を開始しない。外部審査サービスの費用をCloudflareの配信費用に含めてゼロ扱いしない。

通報理由は、権利侵害、無断撮影・プライバシー、嫌がらせ、危険・違法な内容、子どもの安全、撮影記録への疑義、その他。通報者の氏名やアカウントを被通報者へ開示しない。通報の回数だけで機械的に永久停止せず、同一対象の集約、悪用防止、審査履歴、異議申立てを用意する。

### 13.2 子どもの安全と年齢

16歳以上という初期方針と、ストアの年齢レーティングは別に設定する。Google PlayのSocialカテゴリに必要な子どもの安全方針、アプリ内通報、専用連絡先、必要な削除・関係機関への対応手順を整える。年齢制限があることを理由にこの運用を省略しない。[S15]

年齢確認では虚偽申告を完全に防げると説明しない。生年月日の永続保存が不要なら閾値を満たした結果と方針バージョンのみを残し、公開プロフィールへ年齢や誕生日を出さない。地域や対象年齢の拡大時には同意・年齢確認・公開範囲の要件を再評価する。

### 13.3 データ保存と削除

| データ | 初期の保存方針 |
| --- | --- |
| 公開・限定公開の原本とサムネイル | ユーザーが投稿を保持する間、保存枠内で保持。期間だけを理由に自動消去しない |
| 未完了のstaging | コミット後24時間で期限切れ。猶予を考慮した清掃処理で削除 |
| 検証済み未投稿の下書き | 7日。期限と残り日数を本人に表示し、期限後削除 |
| 投稿の検証レシートとmanifest | 投稿と同じライフサイクル。大きな証跡をD1に重複保存しない |
| 生のプラットフォーム検証トークン | 検証に必要な短期間のみ。通常ログへ残さず、必要最小限の結果を保持 |
| 一般アクセス・診断ログ | 初期7日。本文、署名URL、認証トークン、正確な位置情報を記録しない |
| セキュリティ・管理操作ログ | 初期90日。アクセス権限を分離し、用途と削除期限を管理 |
| 通報と審査履歴 | 初期180日。重大案件の保存延長は理由・範囲・期限を個別に記録 |
| バックアップ | 初期30日以内の世代管理。復旧時に削除済みデータを再公開しない |

上表は実装上の初期提案であり、法令や正式な保管契約が指定する日数として扱わない。保持期限は設定化し、プライバシーポリシーの内容と一致させる。

アプリ内からアカウント削除を開始できるようにし、再インストール不要のWeb削除受付も提供する。受付後はログインと新規公開を停止し、投稿、コメント、画像・動画、公開レシート、フォロー、プッシュトークン、ログイン連携を非同期に削除する。Apple連携に必要なトークン失効も行う。[S16][S17]

オンライン系の削除完了目標は受付から7日、バックアップの消失は30日以内とする。共有URLは削除状態を返し、本文や画像を残さない。既発行のメディア許可は最大120秒の猶予を持つ。法的保存が必要なものはアクセスを限定した別の保存範囲とし、理由と期限を管理する。削除台帳は復旧処理にも適用する。

### 13.4 運営画面

運営画面はCloudflare Access等の入口制限とアプリ側の権限管理を併用する。閲覧、審査、利用停止、秘密鍵管理を分け、管理者の多要素認証を必須とする。管理者でも原本を同じIDのまま差し替えられない。すべての審査・復元・停止操作に担当者、理由、時刻、変更前後の状態を記録する。

緊急性の高い通報を優先表示し、通常の審査応答は24時間以内を初期の運用目標とする。実際の対応可能時間・担当者・緊急連絡経路を公開前に確定し、未整備の24時間監視を利用者に約束しない。

### 14.2 共通の仮定

以下は製品の利用予測ではなく、比較のための入力値である。招待制テストの実測を得たら置き換える。

- 月間UUは100万人。平均DAU20万人を標準とし、10万人・30万人の感度を比較する。日間UU100万人は別の規模の比較ケースとする。
- 1か月30日、1日1人60件のコンテンツ閲覧、アプリAPIは1日1人20回。
- メディア要求は1閲覧当たり平均2回。サムネイル、HEAD、Range、再送を含む仮定で、1.5～3回の感度も確認する。
- APIの平均CPUは5ms、メディア認可は1ms。通信待ち時間とCPU時間は区別する。実測前の仮定である。
- 日次利用者の10%が1日に1投稿。投稿の80%が写真、20%が動画。
- 写真は原本とサムネイル合計平均0.4MB。動画容量はポスター込みで保守的に平均4MB、平均視聴時間は20秒とする。動画ファイルの長さと平均視聴時間は別の変数で、最大30秒・6MiBの上限とも区別する。
- 保存は12か月分を想定。期末保存量をGB月の概算に使うため、積み上がる初年度の平均請求より保守的になる。MB・GBは10進表記。12か月で投稿を自動削除する意味ではない。それ以降の蓄積や、利用をやめた人の保存データも含めて再計算する。
- R2読取のキャッシュヒットは0%として計算する。高いヒット率を実現できたと仮定しない。
- 1投稿の基本R2操作はA5回、検証用B2回。Aは原本とサムネイルのstaging・確定保存、およびレシート保存。メディア配信のBは別途加える。
- 投稿本文、フォロー、証跡JSON、バックアップ、再審査、削除ジョブ等の追加費用は次節で扱う。無料保存枠を超えたユーザーの追加投稿は停止するため、継続投稿モデルにはユーザーの入替わりまたは自発的削除が必要になる。

各DAUは1か月の平均値である。比較として、日間UU100万人では同条件の小計は月$3,355.61となる。これは月間UU100万人と同じ利用規模を意味しない。便宜的に1ドル150円で換算すると、上表は約5万・10万・15万円、日間UU100万人は約50万円となる。この換算率は現在の為替レートを示すものではない。

概算式は、月閲覧数＝DAU×60×30、月メディア要求数＝月閲覧数×2、月API要求数＝DAU×20×30。保存GB＝月投稿数×（0.8×0.4＋0.2×4.0）×12÷1,000。R2の課金単位切上げを適用した。小数点以下の精度は入力仮定の確かさを意味しない。

平均DAU20万人でメディア要求の増幅率を変えると、この小計は1.5回で$543.53、2回で$665.93、3回で$910.73となる。1閲覧が必ず1回のHTTP要求になる設計ではない。

### 14.4 別途加算する費用

D1・DO・Queues、検証と通知の追加Worker処理、管理画面、ログ、監視、バックアップ、外部モデレーション、サポート人件費、開発保守、ストア年会費、ドメイン料金は上の小計に含まない。この小計を総運営費や請求上限として示さない。

例えばD1が月5億行を書き込むなら、無料相当枠を引いた書込費用は$450。保存100GBなら追加保存費用は$71.25/月。Queuesに月5,000万個の64KB未満のメッセージを送り、各3操作で処理すると操作料金は$59.60となる。これらは上表のDAUから推定した値ではなく、別の利用量の計算例である。[S20][S21]

フォロワー1人ごとにメッセージを作る方式を避け、複数recipientのIDを上限内でまとめる。D1の書込はまとめても行数に応じて残る。公開投稿の閲覧回数を1回ずつD1に書かず、集約する。1投稿が多数のフォロワーに展開される費用を、投稿ファイル1個の保存費用と混同しない。

保存データを持つ100万人が無料保存枠200MBを使い切ると約200TBとなり、R2保存だけでも公開料金で約$3,000/月になる。月間UU100万人は登録者総数や保存容量の上限を意味しない。利用されない保存データにも費用は発生するため、永続・無制限の無料保存は約束しない。

### 14.5 Streamを初期標準にしない理由

標準ケースの平均DAU20万人、1日60閲覧、動画20%、平均視聴20秒では、動画配信は月2,400万分になる。Streamの公開単価なら配信だけで月$24,000、保存は別となる。平均DAU10万人なら$12,000、30万人なら$36,000、日間UU100万人なら$120,000である。先読み・バッファ等も配信課金に影響する。[S23]

R2では転送量に比例する料金を避けられる一方、エンコード、Range対応、画質と再生品質、認可はアプリ側とWorkers側で実装する。初期は短尺・一定解像度に絞ることでこの負担を抑える。長尺、複数画質への自動切替、ライブが必要になった時点でStream等との費用比較をやり直す。

### 14.6 予算を守る設定

1人200MB、動画30秒・6MiB、写真1MiB、下書きの数と期限、投稿回数、IP・ユーザー・端末別の要求上限をサーバー側で適用する。永続200MB枠とstaging短期枠を別に予約し、期限切れ・失敗・削除はDO・R2・D1の照合後に一度だけ解放する。

運営の月予算を設定し、50%・80%・100%の到達見込みで通知する。80%で広告的な先読みや追加処理を停止し、100%で新規動画投稿等を一時制限する初期運用を用意する。既存メディアの削除や改変を自動で行って費用を帳尻合わせしない。

CloudflareのBudget alertsは通知の機能であり、請求を自動停止する硬い上限ではない。アプリ側の利用制限を実装しても、既存保存や拒否リクエスト等による費用が完全に止まるとは限らない。[S24]

### 14.7 画質を保って費用を下げる改善案

第14.3節はキャッシュ効果をゼロにした保守的な試算である。既存のキャッシュ設計に、端末での重複読込防止と不要な要求の削減を組み合わせる。写真2048px、動画30秒・720p、撮影記録の検証、非公開投稿の認可は維持する。以下の数値は未実測の改善目標で、設定するだけで達成できる値ではない。

月間UU100万人・平均DAU20万人、月3億6,000万閲覧、月60万投稿、12か月分保管という条件で比較する。メディア要求数は端末から実際に出る回数、キャッシュ率はその要求に対してR2の読取を避けられる割合として分けて数える。[S18][S19]

| 案 | 要求回数と配信キャッシュの仮定 | 月額小計 USD |
| --- | --- | --- |
| 標準モデル | 1閲覧2回、キャッシュ0% | $665.93 |
| 要求削減のみ | 1閲覧1.2回、キャッシュ0% | $470.09 |
| 画質維持案 | 1閲覧1.2回、キャッシュ50% | $392.33 |
| 画質維持案 | 1閲覧1.2回、キャッシュ80% | $345.53 |

画質維持案では標準比約41〜48%減を目指す。便宜的な1ドル150円換算では約5.2万〜5.9万円/月となる。これは前節と同じ主要API・配信・保存の小計であり、D1・DO・Queues・追加検証処理・監視・投稿審査・サポート等は別途である。利用をやめた人の保存量、共有Webの流入、追加キャッシュ充填・再試行・grant再取得の増加も実測から加算する。

計算ではアプリAPIを月1億2,000万回、メディア要求を月4億3,200万回とし、キャッシュヒット時もMedia Workerの要求・認可CPUを計上した。R2のB操作は「メディア要求×（1−キャッシュ率）＋投稿数×2」。投稿時の検証用GETは削減せず、端末再利用の効果をキャッシュ率へ再度加えない。追加の充填GETが発生する場合は別途数え、名目のヒット率だけで予算を評価しない。

80%キャッシュ案の内訳はWorkers $187.64、R2保存 $120.81、Class A $9.00、Class B $28.08である。端末からの要求削減と、配信拠点でのR2読取削減を区別して計測する。

### 14.8 改善案の実装と計測

第一に、同じassetとvariantに対する同時取得を1回へまとめる。画面を戻るたびの画像再取得、一覧と詳細の重複取得、不要なHEAD、画面外の先読みを減らす。寸法・形式・サイズは認可済みAPI応答から取得する。動画の再生に必要なRange要求は残し、1.2回という平均目標のために再生品質を落とさない。

端末キャッシュはアカウント・asset・variant・revisionで識別し、アプリ専用領域で暗号化する。公開領域、共有フォトライブラリ、端末バックアップには置かない。初期の端末枠は50MB、最長7日のLRU方式を改善案とし、ログアウト・アカウント切替・退会時には対象キャッシュと鍵を破棄する。これは投稿原本の保存期限とは別である。

キャッシュの保管期間と閲覧権限の期限を分離する。端末に画像が残っていても、表示・再生の開始には現在のviewer・sessionに対応した有効なgrantを要求し、最大120秒の失効条件を延ばさない。期限切れ時は既存のbatch grant経路で再認可し、許可が得られなければ表示しない。復帰時も確認し、通信不能を理由に非公開投稿の閲覧を延長しない。追加の再認可が1日20 API回を超える場合は費用モデルを更新する。すでに保存・撮影された複製まで回収できるとは説明しない。

第二に、Media Workerでgrantとセッションを検証してからCache APIを参照する。内部キャッシュはasset・variant・不変revisionをキーにし、短期署名URLの文字列で断片化させない。内部キャッシュ用の応答ヘッダーと、利用者へ返すprivateな応答ヘッダーを分ける。無認証のR2公開経路や認可前の応答キャッシュは設けない。WAFで認可する別方式は第14.10節の検証候補として扱う。

Cache APIは拠点ごとのキャッシュであり、他拠点への自動複製やTiered Cacheは前提にしない。206応答は保存できないため、Content-Lengthを付けた完全な200応答を保存し、そのキャッシュからRangeを返す。必要な充填GET・重複充填・破棄・再試行を計測する。キャッシュ率50%や80%は実際のアクセス分布次第で、保証値ではない。Cloudflareの前段Workers CachingでWorker実行を省略する案は、認可を飛ばすため本サービスのメディア入口には適用しない。[S09][S18]

第三に、閲覧回数や表示用の集計を閲覧ごとにD1へ書き込まず、時間窓でまとめる。いいね・フォロー・権限・容量の正本は保持する。投稿の配布は利用中のフォロワーを中心にし、人気投稿は読み込み時に統合する現行方式を使う。D1は操作の回数ではなく書込行数とインデックス更新が課金対象なので、単に1つのbatchへまとめただけで行課金が減るとは扱わない。[S20]

月3億6,000万閲覧を1閲覧1行で保存する場合、他の書込やインデックスを除いても、D1の含まれる5,000万行を引いた書込は月$310となる。これは避けたい設計の比較例で、第14.7節の小計へ既に含まれている金額ではない。集計処理自体の費用も別途計上する。[S20]

撮影証跡と原本の照合は投稿時に行い、閲覧ごとに大きな原本のハッシュ計算やプラットフォーム検証を繰り返さない。閲覧権限の確認は続ける。投稿時のサーバー検査や内容審査を省く案は採用しない。KVへ処理を移せば自動的に安くなるとも扱わず、キー単位の読取・書込費用と整合性を比較する。[S29]

実機試験では1,000閲覧当たりのAPI回数、メディア要求、R2 GET・HEAD、充填GET、CPU時間、再生開始時間を写真・動画別に測る。コスト目標と同時に、ログアウト、フォロー解除、非公開化、削除、grant期限切れで表示が止まることを確認する。計測結果を得るまでは、第14.3節のキャッシュ0%モデルを予算の基準として残す。

### 14.9 容量をさらに抑える場合の選択肢

平均保存量を1投稿1.12MBから0.60MBへ減らせば、標準ケースの12か月保有量は8,064GBから4,320GBになり、R2保存は$120.81から$64.65へ下がる。1閲覧1.2要求・キャッシュ80%の場合の主要基盤小計は$289.37となる。追加節約は月$56.16、仮150円換算で約8,400円である。画質を保つ改善案より優先度は低く、この版では動画上限や写真画質の変更を採用しない。

0.60MBの一例は、写真をサムネイル込み平均0.25MB、動画をポスター込み平均2MBとする場合である。動画の短縮や圧縮強化を伴い得るため、30秒動画すべてで現行画質を維持したまま達成できるとはしない。採用する場合も、新しい撮影の原本を確定・ハッシュ化する前に処理する。認証済み原本を同じIDのまま圧縮し直さない。

無料保存枠200MBの縮小は、実際の保存量が減って初めて費用へ反映される。既存投稿を無断で削除する運用にはしない。追加容量の有料化は将来の収支改善案であり、今回の初回リリースへ課金機能を追加する決定ではない。

R2 Infrequent Accessは保存単価が低い一方、読取操作とデータ取出しの料金、最低保管期間がある。頻繁に閲覧されるSNSメディアを一律で移す案は採用せず、将来、長期間読まれない原本が増えた時点で移動費用も含めて比較する。[S19]

### 14.10 追加検証案：WAFで閲覧許可を検証する配信

第14.7節からさらに要求課金を減らす候補として、メディアの配信経路を「WAFのHMAC検証、CDNキャッシュ、R2 Custom Domain」とする。CloudflareはWAFによるR2のアクセス制御と、キャッシュ取得前の検証を公式に案内している。HMAC検証はPro以上で利用でき、Proを月払いする場合は1 zoneあたり$25/月となる。これは未採用・未実機検証の案で、現行のMedia Workerを置き換え済みという意味ではない。[S30][S31][S35]

投稿の検証、セッション確認、最新ACLの確認、短期grantの発行はAPI Workerに残す。配信時のHMACには用途識別子、配信host、有効なsession cookieの値、asset・variant・revisionを含む不変パス、時刻を結び付ける。WAFは同じcookie値を使って検証し、URLだけを別のセッションへ渡しても通らない構成を目指す。公式のconcat対応とcookieフィールドから構成可能と判断した設計案であり、この組合せのzone実行はPoCで確認する。[S32][S33]

WAFのHMAC検証だけで、cookieのJWT期限や現在のログイン状態まで確認できるとは扱わない。発行APIが現在のセッションとACLを確認し、grant期限を「発行から120秒」と「セッション期限」の早い方以下にする。固定TTLを使うHMAC検証へ期限を正しく対応させる方法もPoC対象とする。非公開化・削除・ブロック後は新しいgrantを止め、既存grantによる新規要求は最大120秒で失効させる。取得済みデータや開始済み転送の取消しは保証しない。

キャッシュキーでは認可専用query全体を無視し、内容の違いは不変パスだけで表す。CloudflareはIgnore query stringをPay-as-you-go向けにも提供しており、特定パラメーターだけを除外する上位機能とは区別する。実契約での設定可否、cookie付き要求でもキャッシュを共有できること、利用者に返すキャッシュ指示を確認する。[S34]

R2のr2.devは無効にし、認可されない別Custom Domainや公開経路を残さない。stagingと検証用データは別の非公開バケットに置き、閲覧者へS3 presigned GETを発行しない。許可するmethodはGET・HEADとし、認可回避のSkipルール、cookie・queryの欠落や重複、URIの表現差を拒否する。Rangeも同じ権限で扱う。内部のキャッシュが長期間残っても、すべての新規要求にWAF検証を通す。[S36]

全メディア要求をこの方式へ移し、1閲覧1.2要求・現行画質・第14.7節と同じ利用量を維持できた場合の理論比較を以下に示す。Pro料金を加え、API Workerは月1億2,000万要求・平均CPU 5msとして残している。[S18][S19][S35]

| 費目 | キャッシュ50% | キャッシュ80% |
| --- | --- | --- |
| API Worker | $49.40 | $49.40 |
| Pro 1 zone | $25.00 | $25.00 |
| R2保存・A・B操作 | $204.69 | $157.89 |
| 主要基盤の月額小計 | **$279.09** | **$232.29** |

便宜的な1ドル150円換算では約3.5万〜4.2万円/月。Media Workerを維持する同条件の案より月$113.24下がる。D1・DO・Queues・審査・監視・人件費等の除外範囲は前節と同じである。全メディアを移せない場合や追加APIが増える場合は削減額が小さくなる。キャッシュ率と性能を実測し、下記PoCを通過するまでは確定予算に組み込まない。

採否を決めるPoCでは、異なる有効セッションが同じassetのキャッシュを共有できること、キャッシュHIT時にもトークン欠落・別cookie・期限切れ・別パス・別hostを拒否することを確認する。iOS・AndroidのGET・HEAD・Range、120秒をまたぐ再生とgrant更新、非公開化・削除・ブロック、重複cookie・query、迂回URLも試験する。現行方式と同じ権限保護を満たせた場合に限り、移行の開発工数と月額差を比較して採用を決める。

### 15.2 負荷を段階的に上げる

最初から100万人分の専用サーバーを常時確保せず、招待制、数千DAU、1万DAU、10万DAU、標準ケースの20万DAUへ段階的に計測する。30万DAUと100万DAUは拡張時の試験対象とする。構成が水平分割できることと、その負荷に耐えることを実証済みであることは別である。

標準ケースではWorkers全体で月8億4,000万要求、平均約324要求/秒となる。ピーク係数10を仮定し、約3,240要求/秒を試験対象とする。APIだけでは平均約46要求/秒、ピーク約463要求/秒となる。月間UUだけでは瞬間的な集中量を決められないため、ピーク係数も実測で更新する。

拡張比較として、第14章の日間UU100万人モデルでは、Workers全体で月42億要求、平均約1,620要求/秒になる。ピーク係数10なら約16,200要求/秒を試験対象にする。APIだけでは平均約231要求/秒・ピーク約2,310要求/秒となる。グローバル分散の総量と、1つのD1・人気投稿・同一ユーザーへの集中を別々に測る。

負荷試験は通常の混合アクセス、人気投稿への集中、非公開投稿の権限確認、投稿の一斉送信、R2 Rangeのcache miss、Queue再配送、bucket移動中、削除と配信の競合を含む。費用も実際のusageから1,000閲覧当たり・1,000投稿当たりへ換算する。

Apple・Googleの検証APIの本番利用枠と障害時動作を公開前に確認し、投稿数を増やす前に必要な割当増加を申請する。割当や確認処理の費用を避けるために未検証の投稿へバッジを付ける代替経路は設けない。

期間・予算・人数は見積もり時に確定する。本仕様だけから「数日で100万人運用できる」などの納期は置かない。初期段階でUIより先に実機の撮影認証を検証することで、実現性の大きな不確実性を解消する。

## 17 JustTakenの名称と公開準備

### 17.1 名称と表記

サービス名はJustTaken（ジャストテイクン）とし、この名称で開発を進める。写真の文脈で「いま撮った」という感覚を伝え、日常の写真・動画を気軽に共有するサービスを目指す。旧案のnonAI・MITARINO等はアプリ名に使用しない。

| 項目 | 使用する表記と扱い |
| --- | --- |
| サービス名とアプリ表示名 | JustTaken。JとTを大文字にし、単語間に空白を入れない |
| 日本語の読み | ジャストテイクン |
| 短い説明文 | 専用カメラで撮った写真・動画と、その撮影記録を共有するSNS |
| コピー案 | いま撮った、その瞬間を。 |
| ドメイン候補 | justtaken.app。照会時は取得可能、未取得 |
| 開発用の識別名 | justtaken。法人名、ストアID、所有済みドメインは別途確定する |

名称やコピーは、写っている出来事の真実性や端末内部も含めたAI不使用を保証する表現として使わない。「いま撮った」はサービスの方向性を示すもので、撮影後の下書き保存や時間を置いた公開を禁止するものではない。撮影時刻と公開時刻は区別して表示する。

アプリ表示名、公開ページ、通知の送信者表示、ヘルプ、規約のサービス表記はJustTakenに統一する。ドメイン・ロゴ・ストア識別子は設定で差し替えられるようにする。暗号処理のドメイン分離文字列CAPTURE_SNS_V1は表示名と分離し、名称変更だけを理由に変更しない。
